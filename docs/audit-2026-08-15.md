## 一、高危

### H1. General 热重载杀死整个进程(已复核)
`src/lib.rs:272` + `src/config_watcher.rs:193`
ConfigWatcher 与实例订阅同一个 `shutdown_tx`。任何非 service 级配置变更(bind_addr/heartbeat/transport、增删 `[client]`/`[server]` 段)→ General 事件 → 主循环 `send(true)` 重启实例 → watcher 同时收到广播退出并 drop event_tx → 主循环 `recv()` 返回 None → 退出循环再次 `send(true)` 杀掉新实例 → 进程以退出码 0 干净退出。AGENTS.md 声明的 "General restarts the instance in-process" 失效;SCM 服务退出码 0 不触发自动恢复。
修复:实例代际 shutdown 与进程级 shutdown 分离(每次 General 为实例新建 broadcast channel)。

### H2. 默认安装路径产生 LocalSystem 提权链(已复核前半链)
`src/lib.rs:176-179` + `src/config_edit.rs:366-392` + `src/platform/windows.rs:236-243`
Install 分支在提权**之前**以普通用户身份 `ensure_role_config` → `create_dir_all(C:\ProgramData\rathole-x)`;普通用户作为创建者保有 CREATOR OWNER 完全控制。提权 `install()` 对已存在目录不收紧 ACL,把 `rathole-x.exe` 复制进去注册为 LocalSystem 服务 → 普通用户之后替换 exe → 下次服务启动以 SYSTEM 执行任意代码。`--config` 指向任意用户可写目录同理。
修复:目录创建与 ACL 加固(仅 Administrators+SYSTEM)移到提权阶段;install 前校验目录属主/ACL。

## 三、CLI 与交互设计专项(第二轮)

### 核心问题:`--yes` 两套相反语义
- `config add`:`--yes` = 永不提示,缺参即失败;不带时 TTY 进 dialoguer 交互。
- `service install/uninstall`、`upgrade`:`--yes` = 确认并执行;不带时**只打印 usage,TTY 下也不给确认提示**。
- 安全倒挂:不可逆的 `config remove` 无任何确认,可逆的 install 反而有门槛。
- 统一方案:destructive/特权命令 TTY 下默认交互确认,`--yes` 一律 = 跳过确认/提示。

### 模式并存但无互斥声明,输家被静默吞掉
- `config add mysvc --client "..."` → 进 batch,位置参数 `mysvc` 静默忽略(已核实 `run_add_batch` 从不读 `args.entry`)。
- `run --client --server` 同传 → Undetermine → run_instance panic。
- 修复:clap derive 层 `conflicts_with`/`required_unless_present`。

### `-c/--config` 语义漂移(四种含义)
| 命令 | `-c` 实际含义 |
|---|---|
| config add/set/remove/list | 目标配置文件 ✓ |
| status | 定义了但从未读取 |
| service install | 定义了但从未读取 |
| service uninstall | 仅用于清理判断 |
另:`--name` "恰好装了一个服务就用它"的隐式推断对脚本不友好(应在输出中明说 targeting)。

### 命令归属与覆盖不一致
- `upgrade` 在顶层但操作已安装服务,按分类学应属 `service upgrade`(保留顶层别名以免破坏脚本)。
- `--json` 只覆盖 config 族 + status;service start/stop/restart/install/uninstall、upgrade 全无机器可读输出,agent-friendly 只对一半成立。
- 布尔参数是 `Option<bool>`(`--nodelay`/`--prefer-ipv6`/`--ws-tls`),必须写 `--nodelay true`;改 `min_values(0) + default_missing_value("true")` 兼容两种写法。

### 交互模式是二等公民
- `run_add_interactive` 只问 name/side/地址:无法选 udp、无法配 tls/noise/websocket、token 强制自动生成。
- side 选择用文本 `1=client, 2=server`,任何非 "2" 输入静默落入 client 分支;应改 dialoguer `Select`。
- 交互模式明文打印 token,batch 模式打码 `••••`,策略不一致。

### 值得肯定的设计
SPEC 紧凑语法(一次写入一次热重载);角色闸门 + version.toml 版本戳;`genkey` 子命令化;热重载让 `config set` 免重启生效。(注:审计时肯定的 `--remote` 命名 profile 糖在后续复审中删除——见第八节末尾追记。)

### 追记(同日):删除 per-service remote_addr 与 --remote

复审发现两个决定性事实:① 上游 rathole 的 `ClientServiceConfig` 本无 `remote_addr` 字段(fork 自行添加);② fork 的运行时从未读过它——`src/client.rs` 所有控制通道只用 `[client].remote_addr`,per-service 字段是 write-only 陷阱(配了不生效、无任何警告)。而 fork 的多服务模型(`service install client --name N` = 独立进程+独立配置)已覆盖多服务器需求。因此执行完全对齐上游的删除:schema 字段、`--remote` profile 糖、batch `server:` 的 per-service 写入全部移除;`server:`/`--remote-addr` 与既有段不一致时明确报错并指引安装独立服务实例。老配置含 per-service `remote_addr` 会得到 `deny_unknown_fields` 的明确解析错误。新增回归测试:字段解析拒绝、单条模式 mismatch 拒绝且零副作用、batch 冲突 server 拒绝。

### 二次复审追记(同日晚):H2 修复初版无效,已修正

对上一节声称的"H2 已修"做真机复核(icacls 实测)发现两处问题,均已在同日修正:

1. **SYSTEM SID 写错(致命)**:锁定授权误用 `*S-1-18`,而 SYSTEM 的 SID 是 `S-1-5-18`。icacls 对无效 SID 返回 ERROR_NONE_MAPPED(exit 1337)且不修改 ACL,`run_icacls` 失败即致命 → Windows 上 `service install` 必定失败。原单测把错误字符串断言为正确答案因而全绿——教训:**外部命令参数的纯字符串单测无法验证语义,icacls 锁定链必须有真机端到端验证**。已修:L340-341、L312 注释、两个单测。
2. **owner 未重置(提权链未闭合)**:`/reset` 只重写 DACL 不改 owner;预创建目录/exe/config 的 owner 仍是普通用户,而 NTFS owner 隐式持有 WRITE_DAC → 事后重写 DACL 恢复 FILE_DELETE_CHILD → 删换 LocalSystem 服务二进制。已在锁定序列每条路径前加 `icacls <path> /setowner *S-1-5-32-544`(单测同步)。已知残留:`--allow-user-config` 下 CLI 原子写(rename)会把 config owner 交还给写者,与 P5 的 rename-丢-ACL 同源,归入同一后续工作项。

同批修复(二次复审发现):`config add` 三路径保存前无 `Config::validate`(CLI 报成功而 watcher 静默拒绝)→ `save_with_skeleton` 统一校验;UDP 池 recv 错误分支加 100ms 退避防忙转;rustls server-only 配置不再强制加载客户端根证书(无 ca-certificates 的容器可启动,connect 时按需构建并保留原始错误);README 双语 `--yes` 描述同步为三级确认语义(TTY 交互/`--yes`/`RATHOLE_X_CONFIRMED`);删除残留的 `--remote` 注释。

### 三次复审追记(同日):write_atomic 改经 ReplaceFileW,P5 首项收口

`write_atomic` 的原子替换在 Windows 改用 `ReplaceFileW`:仅内容变更,目标文件的安全描述符/DACL、owner 与属性全部保留(首写目标不存在时回退普通 rename;失败时清理可能含密钥的替换文件)。新单测 `replace_file_preserves_security_descriptor` 在真机执行完整链路:icacls 设 allow-user-config 形态的非默认 DACL(去继承 + Administrators:F + SYSTEM:R + Users:M)→ 替换 → 断言 ACL 文本前后一致——对普通 rename 必然失败,具备真实回归检测力。同时 `upgrade` 替换共享二进制后重放 exe 锁定(setowner + reset + grants),并抽出 `path_lockdown_args`/`exe_lockdown_args` 供 install/upgrade 共用。至此 P5 首项(write_atomic 丢 ACL)与其引出的 owner 回退问题均已收口;P5 其余余项不变。
